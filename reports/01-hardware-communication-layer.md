# 01 — Hardware Communication Layer

This report dissects the lowest layer of the `robochem_flex` self-driving lab stack: the code that sits between Python user procedures and the wires running to physical instruments. All code lives under `Control Software/OmniPlatypus/OmniPlatypus/omniplatypus/devices/`. The design is a single abstract parameter-oriented interface (`BaseDevice`) with three transport-specific subclasses (`ArduinoDevice`, `ModbusDevice`, `SocketDevice`) and a proxy/array pattern for sharing one transport among multiple logical sub-devices.

## 1. `BaseDevice`: the parameter abstraction

`BaseDevice` (`base/device.py:434`) is a pure abstract class. Every physical instrument (`nrg/syringe_pump.py`, `bronkhorst/mass_flow_controller.py`, `magritek/spinsolve.py`, etc.) inherits from one of its transport subclasses and exposes functionality as named parameters rather than method calls. Parameter metadata lives in `DeviceParameter` (`base/device.py:232`) and includes `name`, `access_level` (R/W/RW, `device.py:28`), `value_type`, `min_value`/`max_value`, `caching_policy` (`NEVER`/`TRY`/`ALWAYS`, `device.py:42`), a `stop: threading.Event` for asynchronous abort, and an `internal_id` that is the transport-specific address (an integer Arduino variable number, a Modbus register, a socket command code, etc.).

Parameters are registered by subclass constructors via `BaseDevice.add_parameter` (`device.py:549`), which warns on duplicate names or shared internal IDs. The life-cycle contract is documented at `device.py:482`: constructor → `open()` → `setup()` → `initialize()`. Access before the device is open raises `DeviceNotOpenError`; access before init raises `DeviceNotInitializedError` (`device.py:815–825`).

The pivot of the API is `__getitem__` / `__setitem__`, so user code always reads as `device["pressure"]` and writes as `device["setpoint"] = 3.0`. The read pipeline (`device.py:852`) is:

```python
def __getitem__(self, name: str) -> Any:
    parameter = self._check_device_parameter(name=name, write=False)
    if not parameter.caching_policy == ParameterCachingPolicy.NEVER:
        if parameter.last_known_value is not None:
            return parameter.last_known_value
        ...
    value = self._extract(parameter, self._read(parameter))
    parameter.last_known_value = value
    return value
```

Subclasses only override `_read`, `_write`, and optionally `_extract` (`device.py:749`–`788`). The default `_extract` just calls `parameter.value_type(response)`. Values can be rich objects: `ParameterValue`, `ParameterValueRun` (a guard type for commands that take no argument — you must construct it from the literal string `"RUN"`, `device.py:141`), and `ParameterEnumValue` backed by a `bidict` (`device.py:180`). `Snapshot` (`devices/snapshot.py:12`) captures parameter values and restores them verbatim using the same `[]` accessor; it is intended for settings, not live actuation state.

## 2. Serial transport: `ArduinoDevice`

`ArduinoDevice` (`base/device_arduino.py:361`) wraps `pyserial`. The protocol described in its docstring (`device_arduino.py:364–383`) is deliberately simple and **does not use CRC or checksums** — contrary to what one might assume, the only framing is ASCII with newline terminators:

- Write: `S<id>=<value>\n` (`device_arduino.py:566`, `_command_write`).
- Read: `R<id>\n` (`device_arduino.py:577`, `_command_read`). The response is a newline-terminated ASCII line.

Defaults: 9600 baud, 1 s read timeout, 1 s write timeout, set at `device_arduino.py:419–421`. `open()` writes the comport then sleeps 2 s via `pause.seconds(2.0)` (`device_arduino.py:466`) because opening the port strobes DTR and resets the Arduino. Reliability relies on three mechanisms instead of checksums:

1. **Per-device thread lock**. `_serial_thread_lock: Lock` is acquired around every transaction (`device_arduino.py:710`, `765`). An array of proxies shares the parent's lock so concurrent threads can address different sub-devices of the same Arduino without collisions.
2. **Optional acknowledge values**. A parameter may set `acknowledge_value: str | list[str]` and `read_acknowledge`/`write_acknowledge` flags. `_receive_acknowledge` (`device_arduino.py:632`) spins until one or more whole lines arrive, comparing them to `acknowledge_value`. Failure yields `ParameterTimeoutError` (`device_arduino.py:667`) or `ParameterAcknowledgeError` (`device_arduino.py:691`). Both can be downgraded to warnings via `<param>_ignore_timeout` and `<param>_ignore_badack` setup options auto-generated by `_generate_setup_options` (`device_arduino.py:811`). Example: `nrg/syringe_pump.py:213` sets `parameter.acknowledge_value = "v"` for the pump's volume command.
3. **Device-side error register**. Subclasses may assign `self._error_parameter` to an `ArduinoError` parameter (`device_arduino.py:143`). Every `_read` (except a read of the register itself) and every `_write` calls `_verify_error_register` in a `finally` block (`device_arduino.py:725–729`, `778`). The register encodes errors as `"<type>-<value>"`, parsed by the regex at `device_arduino.py:146`. The `exception()` method (`device_arduino.py:199`) looks up the failing parameter by internal id and raises a typed `DeviceError` subclass.

Additional reliability: `flush_buffer_in` (`device_arduino.py:521`) drains any stale bytes before each transaction; unsolicited bytes become a `ParameterCommError` unless `ignore_unexpected_data_warning` is set (`device_arduino.py:624`). If serial raises `SerialException` or `ValueError`, it is wrapped in `DeviceCommunicationError` (`device_arduino.py:719–723`). There are **no explicit retries** at this layer — a failure escapes to the caller. `reopen()` exists for higher-level recovery (`device_arduino.py:476`).

`ArduinoValue` (`device_arduino.py:37`) is a mixin that provides `to_serial_string`/`from_serial_string`. Parameters may also supply their own callable at `ArduinoParameter.to_serial_string` / `from_serial_string` (`device_arduino.py:286–311`); floats default to `round(value, float_rounding)` with `float_rounding=3` (`device_arduino.py:320`).

## 3. Modbus transport

`ModbusDevice` (`base/device_modbus.py:81`) uses `pymodbus.client.ModbusSerialClient` with `ModbusRtuFramer`. Connection defaults: 9200 baud, even parity, 1 stop bit, 8 data bits, 10 s timeout (`device_modbus.py:104–112`). A per-device `Lock` guards `open`/`close`. Note `is_open()` only returns the cached `self._connected` flag (`device_modbus.py:119`); there is no active liveness probe.

Parameters carry `register_type` — `HOLDING`, `COMMAND`, or `COMMAND_ACTION` (`device_modbus.py:40`) — plus an `internal_id` (address or command code), `internal_type` (`int`, `bin`, `Flag`) and `data_length` in registers. `_read` issues `read_holding_registers` (`device_modbus.py:150`) and, for multi-register values, runs the response through `_ntoh` (`device_modbus.py:143`) which uses `struct` to repack words into the final integer. `_write` distinguishes HOLDING (`write_registers` at the given address) from COMMAND/COMMAND_ACTION, which are always written to address `0x0000` as a pair `[command_code, value]` packed by `_hton` (`device_modbus.py:200–214`). Errors are signalled by pymodbus's `ModbusResponse.isError()`; on failure the response object itself is raised (`device_modbus.py:215`).

## 4. Socket transport

`SocketDevice` (`base/device_socket.py:14`) is a minimal base: it stores `(host, port)`, opens a blocking `AF_INET`/`SOCK_STREAM` socket, and exposes `reopen()`/`close()`. It defines no read/write protocol — each concrete device picks its own framing. Examples:

- `magritek/spinsolve.py:862` sends XML (`self._socket.sendall(request.encode())`) and reads with `recv(4096)` in a polling loop that assembles messages until a parameter-specific `end_of_response` tag is seen (`spinsolve.py:765–771`), with a timeout reset on every received chunk.
- `nrg/rama_berry.py:285` uses a length-prefixed binary frame: first reads 4 bytes of big-endian length, then drains 1024-byte chunks until satisfied.
- `nrg/chromtroller.py:155` wraps every transaction with `self._socket_lock` and uses `keep_open = False` (`chromtroller.py:152`) so it `reopen()`s per call and closes again in `finally` — effectively a lightweight "open → transact → close" RPC style.

There is no built-in automatic reconnection: reconnection is driven externally by whichever layer catches the `DeviceCommunicationError`. `is_open()` is just a null-check on `self._socket` (`device_socket.py:58`), so a half-closed peer will not be detected until the next I/O call fails.

## 5. `ArrayDevice` / `ProxyDevice`

`base/array.py` defines two thin interfaces: `ArrayDevice` holds a dict of sub-devices keyed by name (`array.py:61`, `proxy(name)`), and `ProxyDevice` is a sub-device that stores a reference to its parent but has no transport of its own. The useful specialization is `base/array_arduino.py`: `ProxyArduinoDevice` (`array_arduino.py:15`) is an `ArduinoDevice` constructed with the parent's existing `_serial_iface` and `_serial_thread_lock`, so all proxies share a single serial port and lock. Each proxy has an `array_index` and computes an offset base variable number: `base = _array_parameter_begin + _array_parameter_period * _array_index` (`array_arduino.py:51`), giving the proxy's parameters non-overlapping `internal_id` ranges on the same microcontroller. `open()`/`close()` on a proxy raise `NotImplementedError` (`array_arduino.py:66`). The parent's `setup` step accepts an `array` dict from the config to instantiate named proxies of a class chosen from `_proxy_types` (`array_arduino.py:98–150`), and `initialize()` recurses into every proxy (`array_arduino.py:176`).

## 6. End-to-end trace: `device["pump"] = 1.5`

1. `BaseDevice.__setitem__("pump", 1.5)` (`device.py:897`) logs, then calls `_check_device_parameter` which verifies the device is open + initialized, the parameter exists, is enabled, and accepts writes.
2. `parameter.validate(1.5)` coerces the type (`device.py:291`) and enforces `min_value`/`max_value`; the parameter's `stop` Event short-circuits the write if set.
3. `self._write(parameter, 1.5)` dispatches to the transport. For `ArduinoDevice` (`device_arduino.py:751`): the thread lock is acquired; the receive buffer is flushed and any junk raises `ParameterCommError`; `_command_write` builds `"S9=1.5\n"`; it is `encode("ascii")`d and written; if `write_acknowledge`, `_receive_acknowledge` blocks for `acknowledge_value` (e.g. `"k"` for the syringe pump at `nrg/syringe_pump.py:364`); finally `_verify_error_register` reads the Arduino's error variable and raises the corresponding typed exception if it is non-zero.
4. On success, `last_known_value` is stored (`device.py:935`) so that parameters with a caching policy of `TRY` return the value on next read without another round-trip.

## 7. Error taxonomy

`devices/errors.py` defines a hierarchy rooted at `DeviceError` which stores the originating device (`errors.py:14`). Transport-level failures are `DeviceCommunicationError` and its children `InvalidResponseError`, `NoResponseError`, `FailedWriteError` (`errors.py:46–59`). Access/validation errors at the `BaseDevice` layer are `ParameterError` subclasses carrying the offending `DeviceParameter`: `ParameterAccessError`, `ParameterDisabledError`, `ParameterValueError`, `UnrecognizedParameterName`, plus the Arduino-specific `ParameterParsingError`, `ParameterCommError`, `ParameterTimeoutError`, `ParameterAcknowledgeError` (`errors.py:121–153`). Domain-specific subclasses — `SoftLimitError`/`HardLimitError`/`AlarmLockError` (from Grblr-style motion controllers, `errors.py:164–181`), `HPLCError`, `ValveError`, `MotorError`, `SensorError`, `GpioError` — let procedures catch hardware-category problems without caring which transport produced them. Every exception is logged through `BaseDevice.log_exception` (`device.py:1132`) before being raised, giving a single source of truth in the device log.

---

**Summary (3 sentences)**: Every physical instrument is modelled as a `BaseDevice` whose behaviour is expressed purely as named, typed, access-controlled parameters accessed via `__getitem__`/`__setitem__`; subclasses override only `_read` and `_write` so the high-level API is transport-agnostic. Three transports are provided — a serial `Sx=y` / `Rx` ASCII protocol for in-house Arduino devices (thread-locked, with per-parameter acknowledge values and a device-side error register in lieu of CRCs), a pymodbus-RTU wrapper with register-type-aware read/write, and a bare TCP socket whose framing each concrete device picks itself. Collections of identical sub-units share one physical connection through `ArrayDevice`/`ProxyDevice`, which hand out child `ArduinoDevice` instances bound to the parent's serial interface and lock, with parameter IDs offset per proxy.
